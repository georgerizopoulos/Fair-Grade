# API Spec

Every endpoint in the system: who can call it, what it takes, what it returns, and what errors it can give. This is the contract all four tracks build against. If something here needs to change, whoever changes it edits this file and tells the group out loud before continuing.

---

## Conventions

- **Base URL (local):** `http://localhost:3001`. No `/api` prefix — paths are exactly as written below. The frontend reads the base URL from `NEXT_PUBLIC_API_URL`.
- **CORS:** the backend allows requests from `http://localhost:3000` (the frontend).
- **Format:** every request and response body is JSON (`Content-Type: application/json`).
- **Auth header:** every endpoint except #1, #2, #3 requires `Authorization: Bearer <token>`.
- **IDs:** UUID strings, always generated by the backend, never by the client.
- **Timestamps:** ISO 8601 strings in UTC, e.g. `"2026-10-01T09:00:00Z"`.
- **Points:** numbers, half points allowed (e.g. `1.5`).
- **Lists:** returned in full, no pagination. Each endpoint states its sort order.
- **No update or delete endpoints in the MVP.** Bulk uploads overwrite where stated. To start over, run `npm run seed` (wipes the database and reloads the demo dataset).
- **The LLM API key lives only in the backend `.env`.** The frontend never calls the LLM directly.

---

## Errors

Every error, from every endpoint, has this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "criteria[2].maxPoints must be greater than 0"
  }
}
```

`message` always says exactly what was wrong (which field, which ID).

| `code` | HTTP status | When |
|---|---|---|
| `VALIDATION_ERROR` | 400 | a required field or query param is missing, or a value is out of range |
| `UNAUTHORIZED` | 401 | no token, invalid or expired token, token for a user that no longer exists, or wrong email/password at login |
| `FORBIDDEN` | 403 | valid token, but this role may not call this endpoint |
| `NOT_FOUND` | 404 | a referenced ID doesn't exist |
| `CONFLICT` | 409 | a duplicate (email, `studentIdAnon` within a rubric), or the action can't run in the current state (no answers to grade, grading already running) |
| `LLM_FAILURE` | 502 | AI grading failed for every single answer |
| `INTERNAL_ERROR` | 500 | anything unexpected |

## Database Schema

Γιώργος implements this in `backend/prisma/schema.prisma` (Track 1). He is the only one who edits that file — anyone who needs a schema change asks him.

```
users
├── id             uuid          primary key
├── name           text          not null
├── email          text          not null, unique (stored lowercase)
├── password_hash  text          not null (bcrypt)
├── role           text          not null, 'instructor' or 'ta'
└── created_at     timestamptz   not null, default now()

courses
├── id             uuid          primary key
├── name           text          not null, unique
└── created_at     timestamptz   not null, default now()

rubrics
├── id             uuid          primary key
├── course_id      uuid          not null, -> courses.id
├── question_text  text          not null
└── created_at     timestamptz   not null, default now()

criteria
├── id             uuid          primary key
├── rubric_id      uuid          not null, -> rubrics.id
├── position       int           not null  (1, 2, 3... in the order the rubric lists them)
├── description    text          not null
└── max_points     numeric       not null, > 0
    unique (rubric_id, position)

student_answers
├── id               uuid          primary key
├── rubric_id        uuid          not null, -> rubrics.id
├── student_id_anon  text          not null
├── answer_text      text          not null
└── created_at       timestamptz   not null, default now()
    unique (rubric_id, student_id_anon)

ta_grades
├── id             uuid          primary key
├── answer_id      uuid          not null, -> student_answers.id
├── criterion_id   uuid          not null, -> criteria.id
├── ta_id          uuid          not null, -> users.id (must be a user with role 'ta')
├── points_given   numeric       not null, >= 0
└── created_at     timestamptz   not null, default now()
    unique (answer_id, criterion_id, ta_id)

ai_grades
├── id             uuid          primary key
├── answer_id      uuid          not null, -> student_answers.id
├── criterion_id   uuid          not null, -> criteria.id
├── points         numeric       not null, >= 0
├── reasoning      text          not null
└── created_at     timestamptz   not null, default now()
    unique (answer_id, criterion_id)
```

**Relationships**

```
courses ──< rubrics ──< criteria
               │
               └──< student_answers ──< ta_grades >── users (role = ta)
                                   └──< ai_grades
```

`──<` means one-to-many. `ta_grades` and `ai_grades` also each point at one criterion.

**Why each constraint exists**

- `criteria.position` — the rubric's criteria have a fixed order. The dataset files, the CSV upload, and every response rely on "criterion 1, criterion 2..." meaning the same thing everywhere. Always return criteria sorted by `position`.
- `unique (rubric_id, student_id_anon)` — lets the seed script and the CSV upload find an answer by its student label instead of a UUID.
- `unique (answer_id, criterion_id, ta_id)` — one grade per TA per criterion per answer. `POST /ta-grades/bulk` upserts on this, so re-submitting overwrites instead of failing.
- `unique (answer_id, criterion_id)` on `ai_grades` — one AI grade per criterion per answer. `POST /grade/run` upserts on this, so it can be re-run safely.
- The deviation report is **not a table**. It's computed from `ta_grades` and `ai_grades` every time `GET /deviation` is called (see Deviation Rules). Storing it would mean keeping it in sync whenever grades change.

**Implementation notes**

- Prisma generates UUIDs (`@default(uuid())`) and timestamps (`@default(now())`) the same way on PostgreSQL and SQLite, so switching to SQLite if Postgres is slow to set up changes nothing else.
- Passwords are hashed with bcrypt before storage. `password_hash` never appears in any response.
- Every TA reference is a real user row — there are no free-text TA names anywhere. That's what lets the dashboard show real names and stops a TA from submitting grades under someone else's name.

## Deviation Rules

The single definition of how deviation and flags are computed. Κώστας implements it once, as the pure function `computeDeviation()` in `backend/src/grading/deviation.ts`. `GET /deviation` calls that function — nobody reimplements it.

Two constants, defined at the top of `deviation.ts` and nowhere else:

```
FLAG_RATIO  = 0.15   // gap must exceed 15% of the criterion's maxPoints
MIN_SAMPLES = 3      // at least 3 answers before a gap counts as a pattern
```

**For each TA and each criterion of the rubric:**

1. Take every answer where this TA has a grade for this criterion **and** the AI has a grade for it.
2. For each of those answers: `deviation = taPoints − aiPoints`.
3. `sampleSize` = how many answers that is.
4. `avgDeviation` = the average of those deviations, rounded to 2 decimals. `null` if `sampleSize` is 0.
   - Negative → the TA gives fewer points than the AI (**stricter**).
   - Positive → the TA gives more points than the AI (**more lenient**).
5. `direction` = `"stricter"` if `avgDeviation < 0`, `"lenient"` if `> 0`, `"aligned"` if exactly `0` or `null`.
6. `flagged` = `sampleSize >= MIN_SAMPLES` **and** `|avgDeviation| > FLAG_RATIO × maxPoints`.
   - The threshold scales with `maxPoints` because a 1-point gap matters more on a 2-point criterion than on a 10-point one. On a 2-point criterion the threshold is 0.3; on a 3-point criterion it's 0.45.
7. `examples` = for a flagged criterion, up to 3 answers with the largest `|deviation|`, largest first. For a non-flagged criterion, an empty array.

**For each TA:**

- `answersGraded` = number of distinct answers this TA graded for this rubric.
- `overallDeviation` = the average of `|avgDeviation|` over the TA's criteria that have `sampleSize >= 1`, rounded to 2 decimals. Absolute values, so being stricter on one criterion and more lenient on another doesn't cancel out to "fair."
- `flaggedCriteriaCount` = how many of the TA's criteria are flagged.
- `flagged` = `true` if any criterion is flagged.

**Which TAs and criteria appear:**

- Every TA with at least one grade on this rubric.
- TAs are sorted flagged first, then by `overallDeviation`, highest first.
- Each TA lists **every** criterion of the rubric, in `position` order — including ones they never graded (`sampleSize: 0`, `avgDeviation: null`, `flagged: false`).

## 2. POST /auth/register

**Who can call:** anyone, no token.
**Built by:** Γιώργος.

Creates a user account. No page uses this — the seed script writes the demo accounts directly to the database. It exists so the team can create an extra account by hand (Postman / curl) during development.

**Request body**
```json
{
  "name": "Maria Papadaki",
  "email": "maria@demo.com",
  "password": "demo1234",
  "role": "ta"
}
```

**Response — 201 Created**
```json
{
  "id": "ta-maria-uuid",
  "name": "Maria Papadaki",
  "email": "maria@demo.com",
  "role": "ta",
  "createdAt": "2026-10-01T09:00:00Z"
}
```

**Errors**
- 400 `VALIDATION_ERROR` — any field missing, `role` not `"instructor"` or `"ta"`, invalid email, password shorter than 6 characters
- 409 `CONFLICT` — email already registered

**Notes**
- The password arrives in plain text in the request body and is hashed with bcrypt before it's saved. It's never stored, logged, or returned in plain text.
- The email is stored lowercase.
- This endpoint is open for the demo because everything runs locally. In a real deployment only an instructor or admin could create accounts. If a judge asks, that's the answer — it's a deliberate weekend shortcut, not an oversight.

## 3. POST /auth/login

**Who can call:** anyone, no token.
**Built by:** Γιώργος.

**Request body**
```json
{
  "email": "maria@demo.com",
  "password": "demo1234"
}
```

**Response — 200 OK**
```json
{
  "token": "eyJhbGciOi...",
  "user": {
    "id": "ta-maria-uuid",
    "name": "Maria Papadaki",
    "email": "maria@demo.com",
    "role": "ta"
  }
}
```

**Errors**
- 400 `VALIDATION_ERROR` — email or password missing
- 401 `UNAUTHORIZED` — wrong email or wrong password (same message for both, so it doesn't reveal which accounts exist)

**Notes**
- The password is checked with `bcrypt.compare` against the stored `password_hash` — never by decrypting or comparing plain text.
- The token is a JWT signed with `JWT_SECRET` from `.env`, payload `{ sub: userId, role, name }`, valid for 24 hours (long enough to last the whole event).
- The frontend stores the token in `localStorage` and sends it as `Authorization: Bearer <token>` on every request.
- Logout has no endpoint: the frontend deletes the token.

## 6. POST /rubrics

**Who can call:** instructor.
**Built by:** Γιώργος.

Creates a rubric (a question plus its grading criteria) for a course.

**Request body**
```json
{
  "courseName": "HY335 - Computer Networks",
  "questionText": "Explain how the TCP three-way handshake works.",
  "criteria": [
    { "description": "Correctly names all 3 steps in order (SYN, SYN-ACK, ACK)", "maxPoints": 3 },
    { "description": "Explains what sequence numbers are used for in the handshake", "maxPoints": 3 },
    { "description": "States why a handshake is needed before data transfer (reliability/sync)", "maxPoints": 2 },
    { "description": "Answer is clearly organized and easy to follow", "maxPoints": 2 }
  ]
}
```

**Response — 201 Created**
```json
{
  "id": "rubric-uuid",
  "courseId": "course-uuid",
  "courseName": "HY335 - Computer Networks",
  "questionText": "Explain how the TCP three-way handshake works.",
  "totalPoints": 10,
  "createdAt": "2026-10-01T09:05:00Z",
  "criteria": [
    { "id": "criterion-uuid-1", "position": 1, "description": "Correctly names all 3 steps in order (SYN, SYN-ACK, ACK)", "maxPoints": 3 },
    { "id": "criterion-uuid-2", "position": 2, "description": "Explains what sequence numbers are used for in the handshake", "maxPoints": 3 },
    { "id": "criterion-uuid-3", "position": 3, "description": "States why a handshake is needed before data transfer (reliability/sync)", "maxPoints": 2 },
    { "id": "criterion-uuid-4", "position": 4, "description": "Answer is clearly organized and easy to follow", "maxPoints": 2 }
  ]
}
```

**Errors**
- 400 `VALIDATION_ERROR` — `courseName` or `questionText` missing/empty, `criteria` empty, any `description` empty, any `maxPoints` ≤ 0
- 401, 403

**Notes**
- If a course with `courseName` exists it's reused; otherwise it's created. There's no separate course-management page.
- `position` is assigned from the order of the `criteria` array, starting at 1.
- `totalPoints` is the sum of all `maxPoints`.

## 11. POST /ta-grades/bulk

**Who can call:** instructor, ta. Behaves differently per role (see Notes).
**Built by:** Σταύρος.

Saves TA grades: one entry per answer per criterion.

**Request body**
```json
{
  "taId": "ta-maria-uuid",
  "grades": [
    { "answerId": "answer-uuid-1", "criterionId": "criterion-uuid-1", "pointsGiven": 3 },
    { "answerId": "answer-uuid-1", "criterionId": "criterion-uuid-2", "pointsGiven": 2 },
    { "answerId": "answer-uuid-1", "criterionId": "criterion-uuid-3", "pointsGiven": 2 },
    { "answerId": "answer-uuid-1", "criterionId": "criterion-uuid-4", "pointsGiven": 0.5 }
  ]
}
```

**Response — 201 Created**
```json
{
  "taId": "ta-maria-uuid",
  "taName": "Maria Papadaki",
  "saved": 4
}
```

**Errors**
- 400 `VALIDATION_ERROR` — `grades` empty; `pointsGiven` below 0 or above that criterion's `maxPoints`; a criterion that doesn't belong to the same rubric as the answer; caller is an instructor and `taId` is missing
- 401, 403
- 404 `NOT_FOUND` — `taId` doesn't exist or isn't a TA; an `answerId` or `criterionId` doesn't exist (the message says which)

**Notes**
- **Caller is a TA:** `taId` in the body is ignored. The backend always uses the TA's own user ID from the token. A TA can never save grades under another TA's name.
- **Caller is an instructor:** `taId` is required. This is how the instructor imports grades on behalf of TAs (e.g. from a CSV).
- **Upsert:** if this TA already has a grade for the same answer and criterion, it's overwritten. Re-submitting is always safe.
- All-or-nothing: one invalid entry → nothing saved.

## 13. POST /grade/run

**Who can call:** instructor.
**Built by:** Γιώργος (controller, `grading.controller.ts`) + Κώστας (grading logic, `runGrading()` in `grading.service.ts`).

Has the AI grade every answer of a rubric against the rubric's criteria and saves the results. It does **not** return the deviation report — after it succeeds, the frontend goes to `/dashboard?rubricId=...`, which calls #15. That way the deviation logic exists in exactly one place.

**Request body**
```json
{
  "rubricId": "rubric-uuid"
}
```

**Response — 200 OK**
```json
{
  "rubricId": "rubric-uuid",
  "answersTotal": 18,
  "answersGraded": 18,
  "aiGradesSaved": 72,
  "failedAnswers": [],
  "durationMs": 14200
}
```

If some answers failed, the rest are still saved and the call still returns 200:

```json
{
  "rubricId": "rubric-uuid",
  "answersTotal": 18,
  "answersGraded": 17,
  "aiGradesSaved": 68,
  "failedAnswers": [
    { "answerId": "answer-uuid-9", "studentIdAnon": "student_009", "error": "LLM returned invalid JSON after 3 attempts" }
  ],
  "durationMs": 16800
}
```

**Errors**
- 400 `VALIDATION_ERROR` — `rubricId` missing
- 401, 403
- 404 `NOT_FOUND` — rubric doesn't exist
- 409 `CONFLICT` — the rubric has no answers yet, or grading is already running for this rubric (e.g. a double click)
- 502 `LLM_FAILURE` — every answer failed (usually a wrong API key, no credits, or no network)

**Notes**
- **One LLM call per answer**, grading all of that answer's criteria at once (the prompt is in `TASKS.md`, Track 2).
- **The AI never sees TA grades.** Only the question, the criteria, and the answer text. That's what makes it an independent second opinion.
- **Every LLM response is validated:** each criterion appears exactly once, `0 ≤ points ≤ maxPoints`, reasoning isn't empty. If invalid, retry the same answer up to 2 more times. Still invalid → that answer goes into `failedAnswers` and grading continues with the rest.
- **Up to 5 answers are graded in parallel**, so a full 18-20 answer run takes seconds to tens of seconds rather than minutes.
- **Re-running overwrites** the previous AI grades for this rubric (upsert).
- **The request stays open until grading finishes.** The frontend shows a spinner and must not give up early — no client-side timeout under 120 seconds.
- A rubric with answers but no TA grades yet can still be graded; the dashboard simply won't have anything to compare yet.
